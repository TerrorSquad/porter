A QR slideshow has no return path. The receiver cannot say "I missed 4,102" —
so either the sender loops until every index has been caught, or no individual
index needs catching.

Fountain coding takes the second option.

## The idea

Split the file into `K` source blocks. Each transmitted **symbol** is the XOR of
a pseudo-random subset of those blocks, and the subset is derived from the
symbol's sequence number by a PRNG both sides run independently.

```text
F|seq|K|fileSize|id|payload
```

Nothing about the mapping is transmitted. The receiver reads `seq`, runs the
same PRNG, and knows which blocks went into that XOR.

Collect enough symbols and peeling recovers everything: any symbol that reduces
to a single unknown block reveals it, that block is XORed out of every other
symbol containing it, and the process cascades.

## Deriving a symbol

The PRNG is xorshift32, seeded from the sequence number:

```text
state = seq XOR 0x9e3779b9      // if 0, use 0x9e3779b9
next():
  state ^= state << 13
  state ^= state >> 17
  state ^= state << 5
  return state                   // unsigned 32-bit, wrapping
```

Dart must mask to 32 bits explicitly; Rust's `u32` wraps natively.

Then a degree is drawn from a weighted table, and that many indices are drawn:

```text
r      = next() mod total
degree = smallest d >= 1 with cum_weights[d] > r
indices = {}
while |indices| < degree and |indices| < K:
    indices.add((next() mod K) + 1)
return sorted(indices)
```

The symbol's *effective* degree is `|indices|`, which can be lower than `degree`
when the PRNG repeats an index.

## Two things that look like bugs

::steps{level=3}

### `weights[i]` is not floored to 1

```text
weights[i] = floor(K / (i * (i - 1)))     for i = 2..K
```

This reaches zero once `i * (i - 1) > K`, around `i > sqrt(K)`, and that is what
caps the maximum degree near `sqrt(K)`. Flooring it to 1 would give every high
degree equal weight and make large-`K` transfers effectively undecodable.

### `i * (i - 1)` must be 64-bit

It overflows `u32` once `i > ~65536`, which a large file genuinely reaches — `K`
in the hundreds of thousands. This was a real bug: the product wrapped to a
bogus divisor and corrupted the whole degree distribution.

::

## How many symbols

The sender emits `N = max(K + 20, ceil(K * 3))` symbols before the checksum
frame. The 3× factor is empirical — enough for full peeling recovery from the
complete pool, with margin for scan loss.

The receiver needs materially more than `K` distinct symbols: measured between
1.33× and 1.89× `K` across transfers from K=50 to K=70,965. Progress UI must
scale against roughly 2×`K` or it reads as nearly finished with a third of the
work left.

## Keeping two implementations in step

Sender and receiver derive symbols independently, so any drift breaks decoding
silently — not with an error, but with a file that never completes.

Agreement is verified by shared fixtures rather than by running one language's
tests against the other. `flutter/test/fixtures/fountain_sample.json` holds
known-good symbol derivations; the Rust test suite checks against the same file.

::warning
The transfer id is derived from file content, so the same file sent twice gets
the same id — with a possibly different `K` and `blockSize` if the terminal
changed size. Those two streams are mutually undecodable, so a receiver must key
fountain state on `(id, K, blockSize)`, never on `id` alone.
::
